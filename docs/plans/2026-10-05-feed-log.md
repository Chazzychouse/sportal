# Feed Log Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan
> task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every frame the feeds deliver is logged raw, one fold over the log follows every game (with its plays and
watchability), and the `effect/cluster` game actors are gone.

**Spec:** `docs/specs/2026-10-05-feed-log-design.md` (approved 2026-10-05). ADRs 0008 and 0009 are already written.

**Where to work:** the `../sportal-feed-log` worktree (branch `feed-log`, from `main`). Run
`pnpm install --frozen-lockfile --prefer-offline` there first. Never touch the main checkout. Stop any stray Hub on port
4400 before running one.

**This plan gives signatures, state, tests, and where to look — not bodies.** The implementer writes the code from the
pointers. Read `AGENTS.md` and `node_modules/.pnpm/effect@4.0.0/node_modules/effect/ai-docs/src/` before writing Effect
code; check every API against `apps/hub/node_modules/effect/dist/*.d.ts`.

## Rules for every task

- State is a tagged union with transitions, never booleans and flags. Payloads become domain values through
  `Schema` transformations, not hand-written `x === undefined ? {} : {…}` spreads.
- Effect's own abstractions, never Node's or raw callbacks: `SqlClient`/`SqlSchema` for SQL, the web
  `CompressionStream`/`DecompressionStream` (`"gzip"`) for bodies, as `FastCastPayload.ts` already inflates, `Queue`,
  `PubSub`, `Stream.mapAccumEffect`, `Stream.groupedWithin`, `Schedule`. No `node:fs`, `node:zlib`, mutable classes with
  `Map`s, `for` loops, or `throw` + `Effect.try` (the existing `JsonPatch.apply` wrapper is the one exception).
- Main export first; helpers below as hoisted functions; no option-bag type aliases; no `any`, casts outside
  decoding, non-null assertions, enums, default exports.
- Every exported type name is a `CONTEXT.md` term, added or changed in the same commit (rows in the spec's Glossary,
  plus the deviations below).
- Doc comment on each major export; inline comments only where the why is unclear.
- `pnpm check` passes before every commit. Commits are conventional and end with
  `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Deviations from the spec, to approve here

Found while planning, mostly from the 2026-10-04 recording:

1. **Plays before a snapshot (the spec's open point):** a `Plays` delivery for a game with no live game is dropped
   and counted (`sportal_deliveries_dropped{reason="no game"}`). It cannot happen in log order: a `gp-` topic is only
   subscribed once the fold holds the game. No fourth state.
2. **No unsubscribing.** FastCast's unsubscribe op is not known, and guessing at an undocumented protocol is worse
   than the cost: a `gp-` topic stays subscribed until the socket reconnects, then only current games are
   subscribed again. A finished game's topic is quiet.
3. **`Delivery` has a third case, `Listing { league, games }`** (a poll's whole slate). The fold holds each league's
   last listing, so `Ingest.listed` goes and `Slate` reads only the fold. Glossary: "What a frame said: a league's
   listing, one game's snapshot, or one game's whole list of plays."
4. **A `gp-` document keeps only `/entities/plays`.** Patches are filtered to that prefix (a `copy` by both `path` and
   `from`); the recording has 5 play removals and 5 copies inside plays, none crossing the prefix. `/drives` is not
   tracked: the play list is `entities.plays` ordered by `sequenceNumber`.
5. **The recording cannot replay FastCast whole.** Its checkpoint bodies were never saved, and ESPN's CDN now answers
   404. Every game in it kicked off after the recorder subscribed, and each game's plays arrive as one
   `add /entities/plays`. So the importer seeds each `gp-` topic with a checkpoint of `{"entities":{}}`, leaves out
   the `event-football-nfl` frames, and takes snapshots from the recorded 10-second scoreboard polls.
6. **Replay is quiet.** Replaying the day on startup sets no per-game gauges and logs no events or transitions. One
   `LiveGames.replay` span and one Info line give the count of frames, plays, and games and the duration, then live
   telemetry begins.
7. **New term `Game history`:** the store of derived tables (`plays`, `game_snapshots`).
8. **`PlayKind` splits fumbles:** `fumble` (the offense kept it) and `fumbleLost`. ESPN's types already make the
   distinction, and `Turnover` needs it.

  /** Every frame appended from now on, in `seq` order. */
  readonly frames: Stream.Stream<Frame>
  /** Every logged frame received at or after `from`, in `seq` order, an unchanged poll with its channel's last body. */
  replay(from: DateTime.Utc): Stream.Stream<Frame>
}>()("sportal/hub/FeedLog") {

  /** On `feed.sqlite` in the data directory, its own client so it never shares `sportal.sqlite`'s. */

```

Table `feed_frame` as the spec's, migrated with `Database.migrate("feed", …)`; `kind` in storage adds `unchanged` and
`gap`; `body` is a gzip `BLOB`, `body_hash` a SHA-256 hex (`crypto.subtle.digest`, the web API). Index
`(channel, seq)`.

- `seq` starts at `MAX(seq) + 1` and is assigned under one `Semaphore` permit with the `PubSub` publish, so
  `frames` is in `seq` order.
- Writes: a `Queue` drained by one forked fiber with `Stream.groupedWithin(512, "100 millis")`, each group one
  `sql.withTransaction`. A poll response whose hash equals its channel's last is written as `unchanged` with no body.
- A failed group: logged at Error, counted (`sportal_feed_write_failures`), its frames counted as lost; on the next
  successful write a `gap` row first, its body JSON `{ from, to, count }`. `replay` logs a Warning per gap it passes.
- Closing the layer ends the queue and awaits the writer, within the Hub's 3 s shutdown bound (look at how
  `main.test.ts` checks the bound).
- Metrics: `sportal_feed_frames` (counter by `feed`, `kind`), `sportal_feed_write_duration` (timer),
  `sportal_feed_write_failures`, `sportal_feed_frames_lost`.

- [ ] **Tests first** (`Database.layer(":memory:")`, `TestClock`):
  - appended frames get consecutive `seq`s, and `frames` emits them in order
  - after 100 ms they are in the table; `replay(start)` gives them back equal
  - three identical poll responses on one channel: one body stored, three frames replayed, all with the body; a
    different channel's identical body is stored again
  - `replay(from)` starts at the first frame received at or after `from`
  - a failed write (provide a `SqlClient` whose `withTransaction` fails once) keeps `append` working, then writes a

  - closing the scope flushes frames appended within the last 100 ms

// LiveFeed.ts
export class LiveFeed extends Context.Service<LiveFeed, {
  /** Every frame, as received, for the leagues' scoreboards and for each game in `wanted` (the current games). */
  frames(leagues: ReadonlyArray<LeagueId>, wanted: Stream.Stream<ReadonlyArray<GameSnapshot>>):
    Stream.Stream<Omit<Frame, "seq">, LiveFeedError>
}>()("sportal/hub/LiveFeed") { static readonly none: Layer.Layer<LiveFeed> }
```

- **`EspnProvider.poll`:** the scoreboard request as today, the body as text, `sentAt` from the `Date` header,
  `channel` the league, `kind: "response"`. `slateOf` stays as the decode of a response body.
- **`FastCast.frames`:** each socket text frame is a `message` frame (`channel`: its `tc`, or `"socket"` for `C`/`B`;
  `sourceId`: `mid`; `sentAt`: `ts`). On `H`, it fetches the checkpoint (moved from `FastCastDocument.checkpoint`) and
  emits a `checkpoint` frame with the body, after the `H` frame. On each `wanted` change it sends `S` for every
  `gp-football-<league>-<id>` topic of a wanted game not yet subscribed on this socket; a reconnect starts the set
  empty (deviation 2). It watches each topic's `mid`s: a gap on one topic sends that topic's `S` again, which
  makes FastCast send a fresh `H`, so the document resyncs from a new checkpoint (the spec's "fetch that topic's
